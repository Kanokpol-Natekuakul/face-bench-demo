# Face scan demo

เดโมเว็บภาษาไทยสำหรับลงทะเบียนรูปหน้า แล้วถ่ายอีกภาพเพื่อทดสอบว่าเป็นคนเดียวกันหรือไม่ ใช้ Supabase Edge Function สร้าง face embedding ด้วย YuNet + SFace และเปรียบเทียบแบบ **1:1** ในเบราว์เซอร์ ยังไม่ใช่ระบบเช็คอิน production

- [เปิดเว็บเดโม](https://kanokpol-natekuakul.github.io/face-bench-demo/)
- [โค้ด Edge Function และ benchmark](https://github.com/Kanokpol-Natekuakul/face-bench) — ต้องใช้บัญชีที่มีสิทธิ์เข้าถึง repo

## วิธีใช้

1. เปิด **ลิงก์จาก QR ที่ผู้ดูแลส่งให้ในเบราว์เซอร์ที่จะทดสอบ** หรือกรอก key ที่ได้รับในช่องด้านบน ลิงก์เว็บปกติไม่มี key
2. กด **ถ่ายรูปลงทะเบียน** บนมือถือจะขอเปิดกล้อง บนคอมพิวเตอร์เลือกไฟล์รูปได้
3. รอจนแสดงว่าลงทะเบียนสำเร็จ แล้วกด **ถ่ายรูปเช็คอิน** ด้วยรูปอีกภาพ
4. ดูผลคนเดียวกัน/ไม่ใช่คนเดียวกัน คะแนน และเวลาในการประมวลผล
5. ปุ่ม **ล้างข้อมูลในเครื่องนี้** ลบทะเบียนหน้าและ key ของเดโมในเบราว์เซอร์นี้

QR มี key อยู่ใน URL fragment รูปแบบ `#k=...` หน้าเว็บเก็บ key แล้วนำ fragment ออกจากแถบที่อยู่ อย่าเผยแพร่ QR หรือลิงก์ที่มี key และอย่าใส่ key จริงใน Git

## รูปและข้อมูลเก็บที่ไหน

| ข้อมูล | ที่เก็บตอนนี้ |
| --- | --- |
| รูปที่เลือก | เบราว์เซอร์ย่อ/แปลงเป็น JPEG แล้วส่งให้ Edge Function ประมวลผล โค้ดไม่ได้บันทึกลง Supabase Storage หรือ Database |
| รูปย่อลงทะเบียน + embedding | `localStorage` ของเบราว์เซอร์ ภายใต้ `fb-enroll` เฉพาะเมื่อลงทะเบียนสำเร็จ |
| Key สำหรับเรียก function | `localStorage` ภายใต้ `fb-key` ของ origin เว็บไซต์ |
| รูปเช็คอินและผลเทียบ | แสดงในหน้าที่เปิดอยู่ ไม่ได้บันทึกเป็นประวัติเช็คอินใน Database |

**เปลี่ยนเครื่อง/เบราว์เซอร์ หรือล้างข้อมูลเว็บไซต์ ต้องลงทะเบียนใหม่** ไม่ได้ค้นใบหน้าจากทะเบียนกลางบน Supabase และเดโมนี้ยังไม่ใช้ vector database หรือ `pgvector`

## การทำงาน

```text
รูปที่เลือก → JPEG ในเบราว์เซอร์ → Supabase Edge Function
                                   ↓ YuNet: หาหน้าและตำแหน่งอ้างอิง
                                   ↓ SFace: embedding 128 มิติที่ normalize แล้ว
เบราว์เซอร์ ← embedding + เวลา + ค่าหน่วยความจำ
     ↓ cosine similarity กับ embedding ลงทะเบียน
     ↓ ผ่านเมื่อคะแนน >= 0.363
```

- `site/index.html` เป็นหน้าเว็บและ JavaScript ทั้งหมด ไม่ต้องติดตั้ง frontend dependency หรือ build
- URL function อยู่ในค่าคงที่ `FN` ใช้ `?rt=native` และส่ง key ผ่าน header `x-bench-key`
- ก่อนส่งรูป ถ้าไม่มี key จะแสดงคำแนะนำทันทีโดยไม่เตรียมหรืออัปโหลดรูป
- แยกข้อความ **กำลังเตรียมรูป** และ **กำลังส่งรูปและรอผล** เพื่อไม่ให้เข้าใจผิดว่ารออัปโหลดอย่างเดียว
- คำขอเครือข่ายและการอ่านคำตอบมี timeout 20 วินาที เริ่มหลังเตรียม JPEG เสร็จ ไม่ใช่เวลาสูงสุดรวมตั้งแต่เลือกไฟล์
- เมื่อ function ตอบ 403 จะแสดงช่องให้แก้ key ใหม่ กรณี timeout ไม่ได้ยืนยันว่า key ผิด อาจเกิดจากเครือข่ายหรือ function ได้

## อ่านเวลาและ RAM อย่างไร

- **ประมวลผล** คือเวลาที่ function วัดระหว่างถอด JPEG หาหน้า และสร้าง embedding เป็น elapsed/wall-clock time ไม่ใช่ CPU time ที่แพลตฟอร์มใช้คิด limit
- **ไปกลับทั้งหมด** ในหน้าเว็บเริ่มก่อน `fetch` จนได้ response headers ไม่รวมการเตรียมรูปและการอ่าน response body
- **cold** คือรอบที่ต้องโหลดโมเดล/session เข้า instance ใหม่ ไม่ได้แปลว่ารอบถัดไปจะอยู่ instance เดิมเสมอ
- **RAM** เป็น `heapUsed + external` ที่ function รายงาน ณ เวลานั้น ไม่ใช่ peak memory หรือหน่วยความจำทั้งหมดของ runtime

อย่าใช้ตัวเลขจากรูปไม่กี่ภาพสรุปความแม่นยำ ความจุระบบ หรือรับประกันเวลาในมือถือทุกเครื่อง

### ผลตัวอย่างจากการทดสอบหน้าเว็บจริง

ชุดรูป public-domain 3 ภาพ ผ่าน Chrome บนคอมพิวเตอร์ เรียก function ที่ deploy อยู่จริงในรอบตรวจชุดแก้นี้:

| การทดสอบ | ผล | คะแนน cosine | ประมวลผลใน function | ไปกลับที่หน้าเว็บวัด |
| --- | --- | --- | --- | --- |
| ลงทะเบียน | สำเร็จ | — | 202 ms | 2535 ms |
| รูปอีกภาพของคนเดียวกัน | ผ่าน | 0.779 | 206 ms | 1847 ms |
| รูปคนละคน | ไม่ผ่าน | 0.154 | 190 ms | 1483 ms |

เมื่อจำลองให้เครือข่ายมี latency 30 วินาที หน้าเว็บแสดงข้อความ timeout 20 วินาทีตามที่ตั้งไว้ และเมื่อไม่มี key ไม่ได้ส่งคำขอไป function ตัวเลขเหล่านี้ไม่ใช่ผลทดสอบจากมือถือของผู้ใช้ และยังไม่ได้ยืนยันสาเหตุที่เครื่องผู้ใช้เคยค้าง

## รันในเครื่อง

ต้องมี Python 3 สำหรับเสิร์ฟไฟล์ และ Node.js 22+ สำหรับ regression checks

```sh
python3 -m http.server 8787 --bind 127.0.0.1 --directory site
```

เปิด `http://localhost:8787/` และใส่ key ของ function ที่ต้องการทดสอบ การเรียก function จริงยังใช้เครือข่ายและ quota ของ Supabase เดิม ไม่ได้รันโมเดลบนเครื่อง

ฝั่ง Edge Function ต้องอนุญาต CORS origin นี้ด้วย โค้ด backend ปัจจุบันอนุญาต `http://localhost:8787` และ origin ของ GitHub Pages; เปลี่ยนพอร์ตหรือใช้ `127.0.0.1` ใน URL ถือเป็นคนละ origin

```sh
node --test test.mjs
git diff --check
```

Regression checks ใช้ `node:test` และจำลอง browser/network boundary เพื่อตรวจ missing key, timeout และการแก้ key หลัง 403 ไม่ใช่การทดสอบโมเดลหรือกล้องจริง

## Deploy GitHub Pages

`.github/workflows/pages.yml` อัปโหลดเฉพาะโฟลเดอร์ `site/` ไป GitHub Pages เมื่อ push เข้า `main` หรือสั่ง workflow ด้วยตนเอง ต้องตั้ง GitHub Pages ให้ใช้ **GitHub Actions** ก่อน

README และ regression checks ไม่ถูกอัปโหลดเป็นหน้าเว็บ ไม่ต้องใส่ secret ใน workflow เพราะ key รับจากผู้ทดสอบตอนเปิดเว็บ การ deploy หน้าเว็บไม่ได้ deploy Edge Function ไปด้วย

## ข้อจำกัดและความปลอดภัย

- เป็นเดโมหนึ่งทะเบียนต่อเบราว์เซอร์ ไม่มีบัญชีผู้ใช้ ทะเบียนพนักงานกลาง หรือประวัติเช็คอิน
- การเปรียบเทียบอยู่ฝั่ง browser จึงแก้ไขผลได้ ไม่เหมาะใช้เป็นหลักฐานลงเวลาหรือยืนยันตัวตนจริง
- ยังไม่มี liveness/anti-spoofing จึงไม่ป้องกันการใช้ภาพถ่ายหรือหน้าจอแทนบุคคลจริง
- ค่า threshold `0.363` ยังไม่ได้ปรับและประเมินกับชุดข้อมูลการใช้งานจริง
- Shared key เป็นเพียงตัวจำกัดการเข้าใช้เดโม ไม่ใช่ระบบสิทธิ์รายบุคคล; CORS ไม่ใช่ authentication หรือ rate limiting
- รูปหน้าและ embedding เป็นข้อมูลอ่อนไหว แม้โค้ดไม่บันทึกรูปลง Supabase ก็ยังส่งรูปไปประมวลผลบน cloud และเก็บทะเบียนใน browser ใช้เฉพาะภาพที่มีสิทธิ์และได้รับอนุญาตให้ทดสอบ
- ก่อนใช้จริงต้องออกแบบ authentication/authorization, การเทียบฝั่ง server, liveness, การเก็บ/ลบข้อมูล และประเมินความแม่นยำตามความเสี่ยงก่อน
